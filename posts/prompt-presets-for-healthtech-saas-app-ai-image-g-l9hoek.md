# Prompt Presets for Healthtech SaaS App AI Image Generator Review Aids

Short answer: add the AI image generator behind an asynchronous, policy-gated job boundary, and never let its output become evidence for a healthtech moderation decision. Preserve the uploaded report as the source record; resolve prompt presets and aspect ratios on the server; reserve usage before dispatch; then show the generated image as a clearly labeled review aid beside, not over, the original.

This is an architecture decision about trust boundaries. The deciding constraint is quality versus latency: a slower image can be tolerable, but a plausible image that silently changes what a reviewer believes is not.

## How should a SaaS app add an AI image generator with upload, prompt presets, and aspect ratio guardrails?

Use three separate records: an immutable moderation report, a versioned generation request, and an append-only usage entry. The browser may submit an upload identifier, preset identifier, free-text prompt, and requested ratio. It may not submit the final provider prompt, pixel dimensions, policy version, or charge amount. Those are server decisions.

The report record owns the original text and upload digest. The generation request owns the exact resolved prompt, selected dimensions, model policy, status, and link to the report. The usage entry owns the reservation and final reconciliation. Keeping these records separate makes deletion, replay, and audit rules much easier to reason about. It also prevents a generated derivative from being mistaken for the report itself.

Make the UI boundary blunt: `Generated review aid; not source evidence.` Don't bury that label in a tooltip. A human reviewer should be able to open the original upload and text without loading the generated asset at all.

Prompt presets are policy, not convenience strings. A preset such as `medication-packaging` needs a stable ID and version, allowed variables, a fixed safety suffix, permitted aspect ratios, and an enabled flag. Store the resolved text on each job. If an editor changes version 7 tomorrow, a replay of yesterday's job must still explain what version 6 sent. This resembles message-template governance in regulated notification flows — mutable templates make later investigations needlessly murky.

## Security invariants at the evidence boundary

Four invariants carry most of the design. First, client input never selects arbitrary dimensions or bypasses a preset's variable schema. Second, one idempotency key can create at most one billable generation attempt for a tenant and report. Third, a usage reservation happens atomically with job creation. Fourth, generated bytes live in a different object namespace from user uploads and carry derivative metadata.

No exceptions.

The failure boundary belongs around the queue worker, not around the browser request. Intake should validate the MIME type from decoded bytes, enforce an application-defined byte limit, compute a digest, normalize the ratio to an allowlist such as `1:1`, `4:3`, or `16:9`, and commit the job plus reservation. Only then should it return an accepted job identifier. Invalid preset variables or ratios can return `422`; reuse of an idempotency key with a different payload can return `409`. Those status choices are part of this design contract, not claims about a third-party API.

Keep the reservation pessimistic. Calculate it from the server-owned output class and the maximum permitted attempt count, then reconcile it against actual metered usage after completion. Pricing tables change, so store the pricing-policy version and integer billing units used for the estimate rather than sprinkling currency constants through UI code. There is a catch: reservations can temporarily reduce a tenant's available allowance while work is queued. For a low-volume internal tool, a simple post-use ledger may be a reasonable trade; for a multi-tenant SaaS where concurrent requests can race, reservation is the safer default.

Retries need a narrow definition. A worker can retry a transient transport failure under the same logical job while recording each attempt, but policy rejection and invalid input are terminal. Cap attempts and use jittered backoff. The user-facing state should distinguish `queued`, `running`, `ready`, `rejected`, and `failed` without exposing raw provider messages that may echo prompt content. A dead-letter queue is an operator signal, not a place from which jobs are blindly replayed.

The edge case worth dwelling on is cancellation. Suppose a reviewer closes a report after a job is queued but before dispatch. The worker must re-read report state and policy immediately before it calls the generator. If the report is closed, the reservation is released and no image is produced. If cancellation arrives after dispatch, mark the result ineligible for display, reconcile any actual usage, and apply the derivative retention policy. Trying to promise instantaneous cancellation across a remote generation boundary creates a false guarantee.

## Comparing quality and latency controls

| Option | Request latency | Quality control | Accounting behavior | Suitable use |
|---|---:|---|---|---|
| Generate inside the web request | Highest and variable | Validation is easy to couple to a timeout | Awkward when clients disconnect | Small internal prototypes with no concurrency |
| Queue plus job ledger | Fast acceptance; result arrives later | Policy is resolved before dispatch and rechecked by workers | Reservation and reconciliation are explicit | Multi-tenant production workflows |
| Pre-generate from fixed prompts | Near-zero review latency | Highest consistency, lowest prompt flexibility | Capacity is planned in batches | A small, stable category catalog |

The queue-plus-ledger option fits moderation intake because the reviewer can start with source evidence while the aid is generated. It also gives operators separate latency measures for queue delay and generation time. Don't compress those into one average: a healthy generator behind a saturated queue needs a different response from a slow generation call. Track completion percentiles by output class, terminal outcomes by policy version, reservation age, cancellation timing, and the share of aids reviewers actually open. Avoid logging raw health report text or full prompts; use job IDs, policy IDs, digests, and bounded reason codes.

Evidence stays boring.

I'm not sure a generated review aid improves classification quality for every report category. The evidence needed to settle that is a prospective evaluation against a held-out, policy-approved set, with reviewers blinded to whether an aid is present and disagreement adjudicated by qualified staff. Until then, gate the feature by category and treat usage rate as behavior, not proof of benefit.

## The critical path in Python

The critical path below is deliberately provider-neutral. Repository methods are transaction-aware interfaces, and the dispatch call receives a server-resolved request rather than browser-controlled model parameters.

```python
from dataclasses import dataclass
from typing import Mapping

ALLOWED_RATIOS = {
    "1:1": (1024, 1024),
    "4:3": (1024, 768),
    "16:9": (1024, 576),
}


@dataclass(frozen=True)
class CreateImageJob:
    tenant_id: str
    report_id: str
    upload_id: str
    preset_id: str
    variables: Mapping[str, str]
    aspect_ratio: str
    idempotency_key: str


def create_image_job(command, reports, uploads, presets, jobs, usage):
    report = reports.require_open(command.tenant_id, command.report_id)
    upload = uploads.require_verified(report.id, command.upload_id)
    preset = presets.require_enabled(command.preset_id)

    if command.aspect_ratio not in preset.allowed_ratios:
        raise ValueError("aspect ratio is not allowed by this preset")
    if command.aspect_ratio not in ALLOWED_RATIOS:
        raise ValueError("aspect ratio has no server output mapping")

    resolved_prompt = preset.render_validated(command.variables)
    width, height = ALLOWED_RATIOS[command.aspect_ratio]
    request_fingerprint = jobs.fingerprint(
        report_id=report.id,
        upload_digest=upload.digest,
        preset_version=preset.version,
        resolved_prompt=resolved_prompt,
        width=width,
        height=height,
    )

    with jobs.transaction():
        existing = jobs.find_by_idempotency_key(
            command.tenant_id, command.idempotency_key
        )
        if existing:
            if existing.request_fingerprint != request_fingerprint:
                raise ValueError("idempotency key was reused for another request")
            return existing

        reservation = usage.reserve(
            tenant_id=command.tenant_id,
            output_class=(width, height),
            pricing_policy_version=preset.pricing_policy_version,
        )
        return jobs.enqueue(
            tenant_id=command.tenant_id,
            report_id=report.id,
            source_upload_id=upload.id,
            preset_id=preset.id,
            preset_version=preset.version,
            resolved_prompt=resolved_prompt,
            width=width,
            height=height,
            request_fingerprint=request_fingerprint,
            idempotency_key=command.idempotency_key,
            reservation_id=reservation.id,
            evidence=False,
        )
```

`render_validated` should reject unknown and missing variables, bound each field, and escape or delimit user material so it cannot rewrite the fixed policy suffix. OWASP describes prompt injection and insecure output handling as application risks; a preset does not remove either risk. Generated output still needs policy evaluation, metadata stripping where required, safe content-type handling, and authorization at retrieval.

Test this boundary with property-based cases for ratio allowlists and variable schemas, concurrent requests sharing an idempotency key, cancellation before and after dispatch, quota exhaustion, a pricing-policy change between two jobs, and deletion of a source report while a derivative exists. A deployment should start with shadow job creation that resolves policy and computes reservations without dispatching images, then enable a narrow report category. Roll back by stopping new dispatch while preserving the ledger; never erase in-flight accounting to make a rollback look clean.

## Deployment checks and observability

Treat the policy version as a deployment dimension. Dashboards should separate queue delay from generation time and group terminal outcomes by that version; alerts should use bounded reason codes rather than prompt text. During rollout, compare review turnaround and adjudicated disagreement for enabled and disabled categories. A faster queue is operationally healthy, but it does not establish that the aid improves decisions.

The rollback rule is short: stop dispatch, preserve history.

## Synchronous generation versus a job ledger

Generating during the web request was rejected for this workflow. Remote generation latency consumes request capacity, browser disconnects blur ownership of completed work, and retry behavior becomes entangled with page refreshes. Worse, a reviewer may interpret a timeout as no generation even though remote work has already started. The job ledger gives that ambiguous state a durable home.

Stick with synchronous generation when the feature is an internal prototype, requests are rare, the caller can tolerate the full wait, and there is no tenant allowance to race. Pre-generation is better when prompts form a small controlled catalog and freshness doesn't matter. The queued design is not suitable when the product must deliver a generated asset inside a hard interactive latency budget; in that case, constrain output classes, pre-generate stable assets, or remove generation from the critical interaction.

For healthtech moderation, the final decision stays human-owned. The generated image can help orient attention, but the original report, upload, policy result, and reviewer rationale form the decision record. If evaluation cannot show a quality gain without unacceptable review delay or automation bias, don't ship the aid.
